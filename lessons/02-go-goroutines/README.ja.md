# レッスン 02 – 大勢で同時に遊ぶ

前のレッスンで telnet を 2 つ開いて接続してみましたか？ 2 人目のプレイヤーは、
1 人目が切断するまであいさつすら受け取れませんでした。サーバーが一度に
1 つのことしかしないからです。他のプレイヤーがいない MUD はかなり寂しいので、
これを直しましょう。

## 目標

- **ゴルーチン** とは何かを理解し、`go` で起動する。
- *並行性*（concurrency）と *並列性*（parallelism）の違いを理解する。
- `sync.WaitGroup` で複数のゴルーチンの終了を待つ。
- *レース検出器* 付きでテストを実行する: `./mudschool check --race`。

## ゴルーチン

ゴルーチンは Go のランタイムがスケジュールする軽量スレッドです。とても
安価で、サーバーは何十万個も持てます。関数呼び出しの前に `go` を付けると
起動できます:

```go
go s.handle(conn)   // すぐに戻る。handle は「横で」動く
```

無名関数（クロージャ）でも使えます:

```go
for i := 0; i < 3; i++ {
    go func() {
        fmt.Println("hello from goroutine", i)
    }()
}
```

> Go 1.22 以降、`for` ループの各回は自分専用の `i` のコピーを持ちます。
> 古い Go では、全ゴルーチンが同じ `i` を見てしまうのが定番のバグでした。

複数のゴルーチンが終わるまで待つには `WaitGroup` を使います:

```go
var wg sync.WaitGroup
for _, job := range jobs {
    wg.Add(1)
    go func() {
        defer wg.Done()
        do(job)
    }()
}
wg.Wait()
```

`mudschool_02_test.go` を見てください。テストはまさにこのパターンで
50 個のクライアントに同時送信させています。

## 課題

1. `Serve` を変更し、接続ごとに専用のゴルーチンで処理する。
2. クライアントの接続と切断を `log.Printf` で記録する
   （`conn.RemoteAddr()` でクライアントのアドレスがわかります）。テストは
   ログを確認しませんが、あると便利です。

変更は 1 語とログだけですが、この概念はコースの Go パートで最も重要です。

## 自分で試す

サーバーを起動し、telnet を 3 つ同時に開いて接続してみましょう。次に
`./mudschool check --race` を実行します。レース検出器は、2 つのゴルーチンが
同期なしに同じデータに触れている箇所を見つけます。今はまだゴルーチン同士で
データを共有していませんが、レッスン 05 をお楽しみに！

## 考えてみよう

- 1000 個のクライアントが接続したらどうなるでしょう？ ゴルーチン 1 つの
  メモリはどれくらい？（答え: 必要に応じて伸びる数 KB のスタック）
- `handle` はクライアントを待つ間 `scanner.Scan()` でブロックします。
  今はそれで問題ないのに、レッスン 01 ではだめだったのはなぜ？

## チャレンジ

- 接続中のクライアント数を数えてログに出す: `Server` に普通の `clients int` フィールドを
  加え、`handle` の最初で 1 増やし、クライアントが去るときに（`defer` で）1 減らす。
  `./mudschool check --race` を実行すると `WARNING: DATA RACE` が出るはずです。たくさんの
  `handle` ゴルーチンが同じ変数を同時に変更するからです。`sync/atomic`（`atomic.Int64`）を
  調べて直しましょう。（代わりに `Serve` のループで数えると警告は消えます。それはなぜ？
  そのとき *減らす* のはどこで？ レース検出器が報告するのは、テストの実行中に実際に起きた
  競合だけです。）
