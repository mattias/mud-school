# レッスン 07 – チャット

いよいよ交流です。`say hello` は他の全員に聞こえるべきです。簡単そうですよね。
プレイヤーをループして接続に書き込むだけ。でも、そこには多くの本物の MUD が
はまった落とし穴が隠れています。

## 落とし穴

Ludvig の回線が悪い（あるいは読み込みを止めたバグだらけのクライアントを使って
いる）としましょう。あなたが `say hello` と打ちます。あなたのゴルーチンは Ludvig の
ソケットに書き込もうとします。Ludvig 用の OS のバッファはいっぱいなので、
`Write` は Ludvig が読むまで **ブロック** します。待っている間、あなたのゴルーチンは
ロック `s.mu` を握っているかもしれません。すると誰もログインできず、誰も `who` を
打てません…… *たった 1 人* の遅いプレイヤーがサーバー全体を止めてしまいました。

解決策は Go の定番パターンです:

> **どの接続にも、そこへ書き込むゴルーチンがちょうど 1 つだけある。** 他の全員は
> メッセージを **チャネル**（プレイヤーの送信箱）に入れて、すぐに先へ進む。

```
 goroutine (Anna)   ──┐
 goroutine (Bertil) ──┼──► [ outbox (Ludvig): chan string ] ──► writer goroutine (Ludvig) ──► socket
 ...                ──┘
```

（Anna や Bertil のゴルーチンは Ludvig の送信箱にメッセージを入れるだけ。ソケットに
書き込むのは Ludvig の書き込みゴルーチンだけです。）

## 目標

- バッファなし・バッファ付きの **チャネル** を作って使う。
- `select` と `default` で *ブロックせずに* 送信する。
- チャネルを閉じ、チャネルに対する `range` の動作を理解する。
- バックプレッシャーを理解する: 受信側が追いつかないときどうするか？

## Go の概念

```go
ch := make(chan string, 256)  // バッファ付き: 送信がブロックするまで 256 件入る

ch <- "hi"                    // 送信（バッファが満杯ならブロック）
msg := <-ch                   // 受信（チャネルが空ならブロック）

for msg := range ch { ... }   // チャネルが閉じるまで受信
close(ch)                     // 閉じるのは「送信側」だけ。閉じたチャネルへの送信はパニック！

select {                      // 準備ができた最初のものを選ぶ……
case ch <- msg:
    // 送信した
default:
    // ……何も準備できていなければ、すぐにこれを実行
}
```

チャネル `done chan struct{}` は「データのない合図」の慣用句です。
`close(done)` で `<-done` を待っている全員が目を覚まします。

## 課題

1. **`player.go`**:
   - `Player` に `outbox chan string`（バッファ付き、例えば 256）と
     `done chan struct{}` を追加する、
   - `newPlayer` で `writeLoop` ゴルーチンを起動する。これが `conn` に書き込む
     **唯一の** ゴルーチンで、終了時に `done` を閉じる、
   - `Send` は `select`/`default` でメッセージを送信箱に入れる。送信箱が満杯なら
     プレイヤーを切断する（`p.conn.Close()`）、
   - 送信箱を閉じて `done` を待つ `close()` を書く。
2. **`server.go`**:
   - `except` 以外のログイン中の全員に送る `broadcast(except *Player, text string)` を書く、
   - 誰かが接続したとき（`MsgJoined`: `Bertil さんが接続しました。`）と去ったとき
     （`MsgLeft`: `Bertil さんが去りました。`）に他の人に知らせる。`quit` でも、
     ただ切断した場合でも、
   - 接続を閉じる前に `p.close()` を呼ぶ。でないと `MsgGoodbye` が送られないことがある。
3. **`commands.go`**: `say` を追加する。話した本人には `MsgYouSay`
   （`あなた:「hello」`）、他の全員には `MsgSays`（`Anna:「hello」`）。テキストが
   なければ `MsgSayWhat`（`何と言いますか？`）。

テスト `TestSlowClientDoesNotBlockOthers` は、何も読まないプレイヤーをログインさせ、
別のプレイヤーに約 8 MB のテキストを話させます。素朴な実装ではテストが固まり、
送信箱を使えば合格します。

## 自分で試す

サーバーとクライアントを 2 つ（`./mudschool connect` かレッスン 06 の Rust クライアント）起動し、
自分自身と話してみましょう。`./mudschool check --race` も実行してください。

## 考えてみよう

- `handle` の `defer` の順序は重要です。`p.close()` より先に `conn.Close()` が
  実行されたらどうなる？
- 遅いプレイヤーは切断しています。他にどんな戦略があるでしょう？（メッセージを
  捨てる？ まとめる？ チャットアプリならどうする？）
- ミューテックス + チャネルの代わりに、ゲーム世界全体を所有する *単一の* ゴルーチンに
  全員がコマンドを送る方法もあります。「アクター」パターンと呼ばれることがあり、
  フェーズ 3 のゲームループで使います。
