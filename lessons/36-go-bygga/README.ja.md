# レッスン 36 – ゲーム内での建築

最後のレッスンです。レッスン 31 からは JSON ファイルを編集して世界を変えられます。MUD には
ずっと前からもっと良いものがあります: **オンラインクリエーション**。ビルダーは世界の中を
歩き回り、その場で世界を形作ります:

```
> @dig north Dark cave
北へ掘り進み、"Dark cave"（dark-cave）を作った。
> go north
Dark cave
何もない部屋。@desc で説明を書こう。
> @desc 天井から水が滴っている。暗がりで何かが光った。
完了。
```

変更はすべてレッスン 9 のルールで **検証** され、ワールドファイルに **保存** され、**すぐに
全員に見え** ます。再起動も再読み込みもエディタもいりません。

## 目標

- 生きている状態を安全に変える: 適用し、検証し、結果が正しくなければ **元に戻す**。
- ファイルを **不可分に** 書く: 一時ファイルと名前の変更。クラッシュしても、読む側にも、
  書きかけのファイルは見えない。
- 遅い入出力をゲームループの外に置き、同時に起きる保存の順番を守る。
- 自分の書き込みを見分け、レッスン 31 のファイル監視が再読み込みしないようにする。

## Go の概念

### 適用、検証、元に戻す

```go
func (s *Server) change(fn, undo func()) error {
	fn()
	if err := s.world.Validate(); err != nil {
		undo()
		return err
	}
	return nil
}
```

クロージャが 2 つ。変更するものと、それを取り消すもの。判断するのは世界自身の検証です
（座標と合う出口、同じ場所に 2 つの部屋がないこと など）。建築コマンドに独自のルールは
いりません。

### 不可分な書き込み

```go
tmp, _ := os.CreateTemp(filepath.Dir(path), ".world.json.*")
tmp.Write(data)
tmp.Close()
os.Rename(tmp.Name(), path) // 同じファイルシステム内なら不可分
```

ファイルを開いた人に見えるのは、古い版か新しい版のどちらかで、その中間は決して見えません。

### 順番どおりの保存

JSON はゲームループの **中で** 作り（一貫したスナップショット）、ディスクにはループの
**外で**、ゴルーチンから書きます。素早く 2 回変更するとゴルーチンも 2 つになり、古いほうの
スナップショットが最後に書かれるかもしれません。連番がこれを防ぎます。スナップショットごとに
次の番号を付け、もっと新しいものがすでに書かれていたら、そのゴルーチンはあきらめます。

### 自分を再読み込みしない

レッスン 31 の監視は、ファイルのあらゆる変更を見ます。自分たちの変更もです。だからサーバーは
書いた後にファイルの更新時刻と大きさを覚えておき（`ownWrite`）、監視はそれと一致する変更を
飛ばします。ミューテックス（`saveMu`）で、保存の最中に監視が覗かないようにします。

## 契約

すべて管理者だけ（それ以外は `MsgNotAdmin`）、自分のいる部屋で:

- `@dig <方向> <名前>` – その方向に 1 歩離れた（レッスン 9 の座標）新しい部屋。地形は同じ、
  説明は `MsgNewRoomDesc`、双方向の出口付き。ID は名前から作る（`"Dark cave"` →
  `dark-cave`、重複なし）。`MsgDug`。その方向にすでに出口があれば `MsgExitExists`、名前が
  なければ `MsgDigUsage`。
- `@desc <テキスト>` と `@name <テキスト>` – 部屋の説明と名前。`MsgBuilt`。
- `@exit <方向> <部屋 ID>` – 出口（一方通行）。`@exit <方向> none` で消す。`MsgBuilt`。
- 世界を正しくなくする変更は元に戻し、ビルダーには検証エラー付きの `MsgBuildInvalid`。
- 出口が変わった部屋は新しいゾーンになり、中のものはすべて歩ける位置にとどまる。
- ワールドファイル（`Options.WorldPath`）があれば、変更のたびに世界全体をそこに保存する。
  不可分に、順番どおりに、ゲームループの外で。監視はサーバー自身の保存を再読み込みしない。
  止まるサーバーは、まだ書いている途中の保存を待つ。なければ `MsgNotSaved`。

## 課題

`olc.go` は一部用意されています（`slug`、`newRoomID`、`change`、`rezone`、`cmdDesc`、
`cmdName`、`worldSnapshot`、`finishSaves`、`writeFileAtomic`）。`cmdDig`、`cmdExit`、
`saveWorld` を書きましょう。次に `Server` のフィールド（`saves` は `sync.WaitGroup`）、
コマンド、`watchWorld` のチェック、そして `run` の中: ループが止まるときに
`s.finishSaves()` を呼び、Ctrl+C（や copyover）の直前の変更が失われないようにします。
ついでに Lua の状態（`s.scripts.L.Close()`）とプラグイン（`s.plugins.Close()`）も閉じましょう。

自分だけの小さな地域を作ってみましょう: `-world my-world.json -admin 自分の名前` で
サーバーを起動し、掘り、説明を書き、後でファイルを見てみます。

（ID はラテン文字と数字から作るので、日本語の名前なら `room`、`room-2` のようになります。
動きはしますが、もっと良くするのはチャレンジです。）

## 考えてみよう

- なぜ JSON はゲームループの中で作り、外で書くのでしょう？
- `@dig` は自分で座標を確かめず、世界の検証を使います。利点は？ 欠点はある？
- 出口を加えたとき、手続き生成された部屋のゾーンはどうなる？
- 2 人の管理者が同時に建築したら？ 何がうまくいかない可能性があり、何は大丈夫？

## チャレンジ

- `@undo`: 直近 10 回の変更（取り消し用のクロージャ）を覚えておき、元に戻す。
- `@item` と `@npc`: ゲームの中からアイテムや生き物を作る。
- ビルダー: プレイヤーと管理者の間の役割で、自分の地域でだけ建築できる。
- `@zone`: ゲームの中で、手作りのゾーンを 1 行ずつ描く。
- 日本語の名前からもっと良い ID を作る（ローマ字にする、など）。

**これで最後のレッスンです。** Go でマルチプレイヤーのゲームサーバーを、Rust で
クライアントを作り上げました。エコーサーバーから、光とマウスのあるタイルの世界、保存、
スクリプト、別の言語で書いたプラグイン、そして誰も切断せずにあらゆる面で変えられる
サーバーまで。次にどこへ向かうかのアイデアは `docs/*/CURRICULUM.md` のフェーズ 6 にあります。
